# Обновление правил бронирования и модерации

## Что изменено

- Семь рабочих дней учитывают федеральные праздники и переносы пятидневной рабочей недели РФ на 2026 и 2027 годы. В том числе 20 февраля 2027 года — рабочая суббота.
- Источники: постановления Правительства РФ от 24.09.2025 № 1466 и от 17.09.2026 № 1187.
- День подачи не считается. Срок рассмотрения истекает в то же время суток седьмого рабочего дня по времени организации (Europe/Moscow). Например, заявка от 02.11.2026 12:00 — до 12.11.2026 12:00.
- Если само мероприятие началось раньше окончания срока рассмотрения, неподтверждённая заявка также архивируется: задним числом её одобрить нельзя.
- Фоновый обработчик проверяет сроки независимо от открытых страниц (по умолчанию каждые 30 секунд). Решение по уже просроченной заявке запрещено, даже если обработчик ещё не успел перенести её в архив.
- Просроченная заявка хранится как rejected + archived_at, с отдельной пометкой и системным событием в истории; пользователь видит «Не подтверждена · просрочена», а не «Состоялось».
- Автоматическое завершение подтверждённых мероприятий сохранено. Заявки pending не превращаются в completed.
- У серии единое время подачи; срок не отсчитывается заново для каждой будущей даты. Дополнительные аудитории получают время подачи основной заявки.
- Выбор свободных аудиторий для серии проверяет первую фактическую дату по выбранным дням недели, а не формальную нижнюю границу диапазона. При сохранении проверяются все даты; при согласовании повторно проверяются конфликты.
- В календарь обеих ролей возвращаются только approved и completed, включая подтверждённые блокировки. Pending и rejected туда не попадают.
- Модерация по умолчанию отсортирована по сроку решения; при остатке не более двух рабочих дней карточка выделена. Срок также отображается в карточках обеих ролей.
- Питание и МТО требуют явного ответа «Да» или «Нет» без ответа по умолчанию. Сервер не принимает пропуск или null для новой заявки/серии/переноса. Старые неизвестные ответы не подменяются значением «Нет».
- В БД добавлен уникальный частичный индекс, разрешающий только одного администратора. Если администраторов уже несколько, миграция остановится без автоматического удаления или понижения учётных записей.

## Обновление без Docker

1. Сделайте резервную копию рабочей БД. Учтите: после запуска обработчик архивирует уже просроченные заявки.
2. Остановите backend и frontend. Сохраните существующие DATABASE_URL и SECRET_KEY: не меняйте их ради этого обновления.
3. В папке backend выполните:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

`--reload` предназначен для локальной разработки; на сервере используйте штатный запуск службы.

4. Во втором терминале из frontend: `npm.cmd run dev`. Для размещённого на сервере фронтенда: `npm.cmd run build` и публикация обновлённого dist.
5. Обновите вкладку браузера. Проверьте, что `LIFECYCLE_WORKER_ENABLED=true` (это значение по умолчанию).
6. Если миграция сообщает о нескольких администраторах, остановитесь и определите единственный основной аккаунт. Не удаляйте пользователей или брони для обхода этой проверки.

## Docker Compose

После резервного копирования: `docker compose up -d --build`.
Backend выполняет миграции перед запуском Uvicorn. Не используйте `docker compose down -v`: это удаляет том БД.

## Регистрация

Публичная регистрация с подтверждением корпоративной почты создаёт только обычных пользователей. Роль администратора не выбирается в браузере. Рекомендуется заранее назначить единственный корпоративный адрес администратора; предоставление или передача ему роли — отдельная административная операция с подтверждением владельца сервиса. Для реальной почты необходимо настроить SMTP и ALLOWED_EMAIL_DOMAINS; режим EMAIL_MODE=log не отправляет письма.
